Changes, all in `runner.sh` unless noted:

- **Probe retries (S3, S4, S7).** `case()` takes an `attempted(summary,
  space)` predicate for each of these three cases. A run with no agent turn
  (only API retries, a startup failure, or no assistant event), or in which
  the agent did not attempt the probe step, is retried, at most twice. Each
  retry gets a fresh space copy, a fresh code repo for S7, and a config
  reset. The pause before a retry is 10 s for the first and 20 s for the
  second, and at least 15 s after a capped attempt. The last attempt is
  judged. The detail then starts `retried once after <reason>; ` or
  `retried twice after <reason>, then <reason>; `. If the last attempt has
  no turn either, or does not attempt the probe step, the case fails and
  the detail says `<reason> on the last try, so the probe did not run`.
  Each attempt keeps its own `prompt-<k>`, `stream-<k>`, `summary-<k>`,
  `final-<k>` and `stderr-<k>` files, where `<k>` is the attempt number.
  These cases call `run_agent` with `retry=False`, so the agent run's own
  single retry does not add more retries. That single retry still applies
  unchanged to the other five cases and to test runs (`retry` defaults to
  true).
- **S3.** The long command is now a 90 s wait run by the runner's own
  interpreter:
  `<py> -c 'import select; select.select([], [], [], 90); print("finished")'`.
  The CLI refuses a Bash command whose first part is a bare `sleep <n>` with
  `<n>` at or above its threshold ("standalone sleep"). The Python wait is
  not such a command. The prompt says to make one Bash call in the
  foreground, without `run_in_background`, and not to shorten the command
  or replace it. The probe step counts as attempted when there is a
  foreground Bash call of the wait with one of these outcomes:
  - no result;
  - the exit status of the cap's stop (`Exit code 130|137|143`) in a capped
    run;
  - a result that is neither an error nor a background notice.

  A refusal by the CLI is an error in a run that was not capped, so it
  counts as not attempted and leads to a retry. The judge is unchanged:
  capped, with elapsed time from 30 s up to 40 s.
- **S4.** The prompt now adds that the task is not done until each git
  command it needs (init, add, commit) has been handled by the desk rule,
  each one in the final reply on its own line starting `DESK: `, with none
  skipped and no stopping to ask. The probe step counts as attempted when a
  git command is printed or tried. The judge is unchanged. A run in which
  the agent runs a git command that is not denied, or makes `.git`, still
  fails without a retry.
- **S7.** The prompt now begins by saying the task has no librarian step,
  so the desk rule of the preamble covers none of the steps and no `DESK: `
  line is to be printed. It says step 4 probes the git gate: a denial is
  the outcome the probe looks for, so the agent must make the Bash call, not
  print or skip it. The probe step counts as attempted when all four tool
  calls were made: the Read and the Write in the repo, the `git log` call,
  and the `git -C <repo> commit` call (made, or in the permission denials).
  The judge is unchanged. A commit that runs and is not denied still fails
  without a retry.
- **Pause after a capped case.** After a case whose run was capped
  (normally S3), smoke now waits 15 s before the next case. In 7 of 10
  earlier smoke runs on this node, S4 (the case right after S3) got only API
  retries on its first try. In the 4 runs since the pause was added, S4 has
  passed on its first try each time. That is a small sample, and the cause
  of the stalls is not known.
- **README.md.** Updated the S3, S4 and S7 rows of the smoke table. Added
  the paragraphs "Probe retries (S3, S4, S7)" and "Pause after a capped
  run". Added a pointer to them from Caps.

  three final runs below, back to back, at the final state of both files.

## Concerns

- **The S3 fix is not tested on linux-server.** This node does not refuse a
  90 s shell `sleep`, so the refusal cannot be reproduced here. The lead's
  linux-server run is the test. If the CLI refuses the Python wait too, S3
  retries twice and then fails with `probe step not attempted on the last
  try`, which names the cause.
- **The pause after a capped case is a mitigation.** The cause of the API
  stalls after a capped run is not known. If they come back, the probe
  retries absorb up to two of them in S3, S4 and S7. In the other five
  cases, the one retry inside the agent run absorbs one.
- **One read beyond the brief.** To see a report layout, I read the first
  30 lines of the T39 report, `20261028T0053Z-T39-report.md`, before
  finding the template (`templates/records/report.md` in swe-pod). The
  brief allowed no report but T15's. Nothing in those lines bears on this
  task, and none of my changes draws on them.
- **Observation, not changed: S7's repo.** The S7 code repo is a depth-1
  clone of the `--gate` checkout's current HEAD, not of the `--gate` sha.
  In the final runs, its `git log` showed a later agent-mesh commit than
  `e0f6af0`. This does not change what S7 shows. The README's wording, "a
  depth-1 clone of the `--gate` checkout", is accurate.
- **Observation, not changed: kept stderr.** A startup failure writes the
  CLI's error to `stderr-<k>.txt`, and that error includes the provider
  gateway's URL. The redaction does not rewrite that URL. Run dirs stay on
  the node, so this matters only if a kept stderr file is ever quoted.
